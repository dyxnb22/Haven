## 3. 两个项目共用的阅读方法

不要从目录第一行开始顺序阅读，也不要一开始研究所有配置。每条简历主张都按下面的方向读：

```text
简历主张
  → 用户或业务问题
  → HTTP / CLI / Job / MQ 入口
  → 应用层编排
  → 核心规则
  → 数据状态变化与外部副作用
  → 失败、重试、补偿或停止
  → 测试如何证明关键分支
  → 面试中的边界表述
```

### 第一遍：只画骨架

目标是回答“请求从哪里进、最后到哪里结束”。只看类名、方法签名、依赖和返回值，不钻实现细节。输出一张不超过 12 个节点的流程图。

### 第二遍：跟正常主链路

逐个方法记录：输入是什么、读取什么状态、写入什么状态、调用什么外部系统。遇到接口时先看接口语义，再找当前实际注入的实现。

### 第三遍：专门跟失败链路

重点搜索 `catch`、状态枚举、条件更新、唯一键、重试任务和恢复逻辑。对每个外部调用都问：

- 调用前有没有保存业务意图？
- 超时后能否判断对方是否成功？
- 重试会不会产生重复副作用？
- 哪个业务键负责去重？
- 无法证明结果时，系统继续、补偿还是停止？

### 第四遍：用测试反向确认

测试通常比大段实现更快地暴露设计不变量。先读测试名称，再回到生产代码寻找它为什么能够成立。每条简历主张至少找一个正常用例和一个失败用例。

## 4. 每次学习必须留下的成果

每完成一个主题，至少留下下面五项内容：

1. 一张主链路图。
2. 一张状态变化表。
3. 一个失败场景及恢复过程。
4. 三个面试追问和自己的回答。
5. 一段 60～90 秒、不依赖类名的口述。

如果只能复述“用了 Redis、RabbitMQ、DDD”，但不能说出数据在何时写入、失败后停在哪里，就还没有学会。

## 6. 一次 90 分钟学习单元

| 时间 | 任务 |
| ---: | --- |
| 10 分钟 | 读一条简历要点，写出 3 个需要代码回答的问题 |
| 20 分钟 | 找入口、编排器、接口和实现，画骨架 |
| 25 分钟 | 跟正常主链路，填写状态变化 |
| 20 分钟 | 跟失败分支和相关测试 |
| 10 分钟 | 不看代码口述，并录音回听 |
| 5 分钟 | 写下仍不确定的问题，安排下一次复习 |

## 7. 学会的判断标准

一个主题只有同时满足下面条件才算通过：

- 能在 2 分钟内定位入口和关键实现；
- 能不看代码画出主链路；
- 能说清至少一个持久化状态和一个幂等键；
- 能解释一个崩溃窗口或超时场景；
- 能比较当前方案与一个更简单方案的取舍；
- 能主动说明简历没有声称的内容，例如生产吞吐量、零超卖、Exactly Once、完整容器隔离。
