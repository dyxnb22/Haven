# 面试复习与回答方法

这份文档负责把代码理解转换成面试表达。核心原则：先回答业务问题，再讲设计；先讲主链路，再讲失败；最后主动限定结论。

## 1. 项目讲解顺序

目标是 Java 后端岗位，建议按以下顺序：

1. 先讲企业工作经历，证明真实协作、交付和问题定位经验；
2. 主项目讲 Big-Market，展示 Java、Spring、MySQL、Redis、MQ、RPC 和一致性设计；
3. Haven 作为补充，展示 Python、Agent 工具调用、安全边界和恢复设计；
4. 面试官没有追问 Haven 时，不主动把对话带到模型 API 或 TUI 细节。

项目定位统一说“作品集项目”。重点放在当前实现与取舍，不讨论是否原创，也不把它包装成生产商业系统。

## 2. 通用回答公式

任何项目问题都按七步回答：

```text
结论
  → 业务问题
  → 约束
  → 正常流程
  → 状态与幂等
  → 失败处理
  → 取舍和边界
```

示例问题：“你怎么保证积分不重复发？”

> 核心不是保证消息只投递一次，而是让重复投递不产生重复入账。中奖履约阶段先用条件更新推进中奖状态，并在同一事务写积分待发任务；后台任务用中奖订单号调用 Account，Account 再把同一订单号作为业务流水号做唯一约束。任务如果在远程成功后、本地标记完成前崩溃，会再次调用，但账户侧返回已有结果，不再次加积分。这里实现的是至少一次调用下的业务幂等和最终一致性，不是 Exactly Once。

这段回答包含业务目标、事务边界、幂等键、崩溃窗口和边界，比“用了 Outbox + Redis 锁”更有说服力。

## 3. 防止回答发散的方法

### 先给范围

开头限定自己要讲的链路：

> 我先按一次抽奖从同步请求到积分到账讲，核心分成参与订单、策略选奖、库存确认和异步发奖四段。

### 只保留一个主键

一条链路中始终追踪一个业务标识：

- Big-Market：`orderId / awardOrderId / outBusinessNo`；
- Haven：`run_id / call_id / approval_id` 与文件前像摘要。

主键能把分散的表、消息和日志串成同一件业务事实。

### 每个名词马上解释作用

不要说“用了 DDD、Outbox、CAS、TOCTOU”。改成：

- DDD：活动用例依赖策略和奖品端口，不直接依赖 Redis 或具体服务类；
- Outbox：业务记录和待发送任务同事务落库，MQ 失败后仍能扫描恢复；
- CAS：只允许从预期旧状态推进，重复处理更新 0 行；
- TOCTOU：用户批准后、真正写文件前再次比较文件摘要，防止批准基于旧内容。

### 最后主动收边界

常用句式：

- “当前代码能证明的是……，没有生产压测数据，所以我不会扩展到 QPS 结论。”
- “这里保证的是业务幂等和最终一致，不是消息 Exactly Once。”
- “这是操作系统进程限制，不等同于虚拟机或完整容器。”
- “无法证明远端结果时保留待确认状态，而不是把超时当成明确失败。”

# 一、Big-Market 面试表达

## 4. 30 秒版本

> Big-Market 是一个 Java 后端作品集项目，核心流程是用户参与活动、按策略选奖、校验次数和库存，再异步发放奖品。同步抽奖中，我用活动应用服务串联参与订单、责任链和决策树、中奖记录以及库存确认；概率结构在活动启动时预装到 Redis。可靠性上，库存使用订单号做预占、确认和释放，中奖记录与待发消息同事务保存，积分奖再通过第二层任务异步调用账户服务，并用业务订单号防重复入账。

30 秒版本只用于建立地图，不展开类名和所有中间件。

## 5. 2 分钟版本

> 这个项目解决的是营销活动中的抽奖和异步履约。业务上分成活动、策略、奖品和积分账户，活动应用服务负责一次抽奖的编排，通过端口调用策略和奖品能力。用户请求进来后先创建或复用参与订单；新建订单时在本地事务里扣总、月、日额度。之后责任链先处理黑名单和累计积分分段，再从提前装配的概率结构中得到候选奖，决策树继续检查奖品解锁次数和库存。
>
> 概率精度不高时，我把概率展开成随机索引表放入 Redis，抽奖阶段是随机下标加 Hash 查询；离散范围超过 10000 时改用累计区间，避免查找表过大。有限库存奖品用参与订单号作为预占 ID，Lua 原子完成去重和 Redis 扣减，MySQL 持久化记录负责保存最终可恢复事实。中奖记录保存失败才释放库存；已经保存成功但确认入队失败时，不能释放，而是写补偿任务继续确认。
>
> 发奖采用本地消息表。中奖记录、待发消息和参与订单状态在同一事务提交，MQ 发送失败由任务扫描恢复。积分奖消费后，再通过条件更新中奖记录并写积分发放任务，后台调用 Account；账户以中奖订单号作为业务流水号幂等。RPC 超时时先查询流水，仍不能确认就进入待对账状态。这套设计提供最终一致性和重复调用下的业务幂等，不声称 Exactly Once 或生产容量指标。

不要机械背诵。每次练习随机删掉一段，再用自己的语言补全，确保理解的是关系而不是固定句子。

## 6. 五条简历要点的展开锚点

| 简历主题 | 先说什么 | 必须落到的代码事实 | 最后收什么边界 |
| --- | --- | --- | --- |
| 业务流程与模块 | 一次抽奖分同步和异步两段 | `executeDraw`、三个 Port、Market/Message-Job/Account | 模块边界不等于所有调用都远程化 |
| 概率装配 | 热点路径不重复计算概率 | 预装配、10000、Hash 表、累计区间 | 阈值不是压测结论 |
| 抽奖规则 | 先确定范围，再判断能否发 | 责任链、规则树、接管后仍查库存 | 不是通用规则平台 |
| 库存一致性 | 预占、确认、释放三阶段 | `reservationId`、Lua、持久化记录、补偿 Job | 不声称强一致或零超卖 |
| 积分发放 | 重复调用不重复入账 | 两层 Outbox、CAS、`awardOrderId`、UNKNOWN 对账 | 最终一致，不是 Exactly Once |

## 7. Big-Market 深挖题

### Q1：为什么先创建参与订单，再抽奖？

回答锚点：参与订单把一次抽奖额度变成可持久化、可复用的业务意图。若进程在扣额度后中断，下次找到 `create` 状态旧单继续，不再重复扣。中奖事务最终将订单从 `create` 条件更新为 `used`，阻止同一订单产生两次中奖。

### Q2：为什么概率表放 Redis，不每次用数据库概率计算？

回答锚点：活动配置变化频率低于抽奖请求，适合把计算移到装配阶段；热点查询只随机取下标并查缓存。代价是缓存空间、预热和配置失效复杂度。高精度导致离散范围过大时改用累计区间。

### Q3：O(1) 是否包括预热？

回答锚点：不包括。O(1) 描述抽取阶段的索引查询；装配仍需要按概率填充、打乱和写缓存，时间和空间都与离散范围有关。

### Q4：为什么责任链后还需要决策树？

回答锚点：责任链适合有顺序的前置分流，决定从主表、权重子集还是固定范围产生候选奖；次数与库存会产生分支和备用奖，更适合树。候选奖被接管也不代表库存已预占，因此仍进入后置树。

### Q5：为什么 Redis 扣库存后还要 MySQL 记录？

回答锚点：Redis 负责热点原子预占和快速重复判断，但缓存键可能过期或丢失，也存在 Redis 标记与数据库事务之间的崩溃窗口。持久化扣减记录按 `reservationId` 保存可恢复事实，并和 MySQL 库存扣减同事务提交。

### Q6：中奖记录保存失败时，先返还次数还是先释放库存？

不要只回答顺序，先说不变量：中奖事实不存在时，本次额度和有限库存都不应被永久消耗；两项补偿都必须幂等。当前应用服务先尝试释放已预占库存，再调用活动账户端口补偿参与额度；补偿自身失败会记录错误，需要继续治理。

### Q7：中奖记录成功后库存确认失败，为什么不回滚中奖记录？

回答锚点：中奖记录与参与订单状态已经在本地事务提交，构成用户可见事实。此时释放库存会使同一库存再次被别人抽中。正确方向是保留中奖事实和预占，写待确认任务继续推进数据库库存。

### Q8：为什么 MQ 重复不会重复发积分？

回答锚点：重复消息仍可能到达。第一层消费只把明确的重复业务码视为已处理；积分阶段用中奖记录状态 CAS 和任务唯一键阻止重复建任务，Account 再用 `outBusinessNo=awardOrderId` 防止重复账户流水。锁只减少并发冲突，最终依赖持久化约束。

### Q9：RPC 超时后为什么不直接重试？

回答锚点：超时不说明远端未执行。先用同一业务号查询 Account 是否已有流水；有则按成功收口，没有且仍不能确认时持久化待对账任务。后续即使重试也使用同一幂等号。

### Q10：这套方案最大的复杂度是什么？

可从三点回答：状态和任务表增多；需要监控积压、失败和人工处理状态；缓存、数据库和远端账户之间需要对账。它适用于副作用不能丢也不能重复的链路；简单低价值操作可能不值得使用两层 Outbox。

# 二、Haven 面试表达

## 8. 30 秒版本

> Haven 是一个本地 Coding Agent 作品集项目。模型只负责提出读取、编辑或命令请求，程序通过严格参数校验、工作区事实、权限策略和必要审批决定是否执行；批准后还会复核文件版本，并生成绑定本次操作的执行凭证。任务结束时不相信模型自报完成，而是要求最后修改后的差异和注册检查通过。SQLite 保存事件、检查点和副作用执行记录，中断后无法证明是否完成的操作不会自动重放。

## 9. 2 分钟版本

> Haven 的核心问题不是如何再封装一个模型接口，而是如何让不确定的模型在本地工作区执行工具时保持可控。运行层由 `RunService` 驱动 Model、Tool、Observation 循环，并用步骤、工具次数、时间、Token 和成本设定上界。接口、应用、领域、端口和适配器分层，组合根负责把模型、文件系统、SQLite、进程执行器和操作系统沙箱接入核心。
>
> 每个工具调用都经过同一条执行通道：先确认工具注册并用 Pydantic 严格校验参数，再由程序读取路径、保护目录、文件前像和沙箱等事实，纯函数策略给出允许、询问或拒绝。需要审批时，摘要绑定工作区、工具版本、规范参数、文件前像和预览，数据库条件更新保证批准只消费一次；用户确认后程序再次比较前像，避免文件在批准与执行之间变化。通过后才生成内部执行凭证，原始模型 JSON 不直接进入执行器。
>
> 完成判断由 Evidence Gate 负责：只要写过文件，最后一次写入后必须有非空 diff 和通过的注册检查，并通过有限的固定规则审查。任意 `exec` 返回 0 不能冒充验证。副作用执行前记录 STARTED，成功后记录 CONFIRMED；进程在中间退出则标记 UNKNOWN。恢复时文件操作可通过前像和后像分类，无法证明或进程类副作用需要人工处理。这里的沙箱是 Seatbelt/Landlock 进程限制，不是虚拟机；固定审查也不是完整安全扫描。

## 10. 五条简历要点的展开锚点

| 简历主题 | 先说什么 | 必须落到的代码事实 | 最后收什么边界 |
| --- | --- | --- | --- |
| 运行控制 | 有界 Agent Loop | `_drive`、State/Context/Result/Trace、五类预算 | 本地单活跃运行，不是多代理平台 |
| 工具执行 | 模型提议与实际副作用隔离 | Registry、Schema、Facts、Policy、Ticket | Ticket 是内部授权载体 |
| 审批一致性 | 批准一项精确操作 | 六类摘要输入、单次消费、TOCTOU | 不等同文件系统事务隔离 |
| 完成与沙箱 | 成功由程序证据定义 | 最后写入后的 diff/check、固定审查、进程限制 | 不保证代码绝对正确或完整隔离 |
| 中断恢复 | 未知副作用不盲目重放 | STARTED、前后摘要、EFFECT_UNKNOWN、reconcile | 本地恢复，不是分布式工作流 |

## 11. Haven 深挖题

### Q1：为什么不让模型直接调用文件和进程 API？

回答锚点：模型输出属于不可信输入，可能参数错误、越界、受提示注入影响或与用户看到的内容不一致。统一通道把自由文本转换为严格 DTO，再用程序事实和策略控制权限，使执行边界不依赖模型自律。

### Q2：策略和审批有什么区别？

回答锚点：策略先根据程序事实给出 ALLOW/ASK/DENY。审批只处理 ASK，代表用户接受一项精确副作用；路径越界、保护路径或必需沙箱缺失等 DENY 不能由用户按钮覆盖。

### Q3：审批为什么要绑定 preimage 和 preview？

回答锚点：preimage 指用户批准时的文件版本，preview 指用户实际看到的变更。如果文件或预览变化，旧批准不能安全重用。二者分别绑定输入状态和预期修改。

### Q4：已经绑定 preimage，为什么执行前还要再读一次？

回答锚点：摘要只记录批准时的事实，无法阻止另一个进程在之后改文件。执行前复核才能发现检查与使用之间的变化，失败时返回 stale preimage。

### Q5：ExecutionTicket 是否能防所有绕过？

回答锚点：不能。它保证当前程序内部的执行处理器接收已经验证和授权的调用摘要，阻断原始模型 JSON 直达；整体安全还依赖没有旁路执行器、路径规范化正确、适配器遵守契约以及 OS 沙箱。它不是跨进程签名凭证。

### Q6：为什么 diff 和 test 都要在最后一次写入之后？

回答锚点：任何后续修改都会使旧观察失效。事件序号把证据与最后写入排序，保证验证针对最终候选变更，而不是较早版本。

### Q7：为什么 `repo.exec` 不能算检查？

回答锚点：任意命令由模型自由选择，可能是 `true` 或只检查无关部分。`repo.check` 只能引用项目预先注册的配方，命令和权限来自可信配置，因此可以成为完成证据。

### Q8：Evidence Gate 能否保证代码正确？

回答锚点：不能。它保证有可归因净变更、运行了注册检查且固定审查未发现少量明显问题。测试覆盖、配方质量和未检查风险仍然决定实际正确性。

### Q9：为什么命令中断后不能像文件编辑一样判断？

回答锚点：文件编辑有目标路径和预期前后摘要；命令可能影响网络、子进程或多个未跟踪位置，当前磁盘状态不能证明它是否运行。自动重放可能重复外部副作用，因此进入 unknown。

### Q10：事件日志和检查点为什么同时存在？

回答锚点：事件日志保留发生过什么，适合审计和重放；检查点保存某时刻聚合后的运行状态，恢复快。执行记录还单独保存副作用边界。只用一种会在性能或可证明性上不足。

# 三、专业技能如何与项目对应

## 12. 不要把技能表背成名词清单

| 技能分类 | 项目证据 | 面试前要补的基础题 |
| --- | --- | --- |
| Java / Spring Boot | Big-Market 应用服务、领域服务、事务、Bean 作用域 | IOC/AOP、事务失效场景、异常与并发 |
| MySQL | 额度条件更新、Outbox、库存记录、积分流水 | 索引、事务隔离、唯一键、死锁、SQL 优化 |
| Redis/Redisson/Lua | 概率表、库存预占、锁、延迟队列 | 数据结构、过期、原子性、缓存一致性、锁续期 |
| RabbitMQ | 发奖消息、重复消费、DLQ | 至少一次、ACK、重试、顺序、积压 |
| Dubbo/Nacos | Message-Job 到 Account 的 RPC | 超时、重试、服务发现、序列化、熔断 |
| XXL-Job | Outbox、库存确认和远程对账 | 分片、重复调度、幂等、失败告警 |
| DDD / 设计模式 | Port、聚合、责任链、决策树、模板方法 | 为什么使用、增加的复杂度、适用边界 |
| Python / asyncio | Haven Agent Loop、流式客户端 | 事件循环、Task、取消、超时、同步 I/O 阻塞 |

| Agent 安全 | 工具通道、审批、Evidence、沙箱、恢复 | 信任边界、TOCTOU、失败关闭、未知副作用 |

复习技能时，每个名词至少准备“项目在哪里用、解决什么问题、失败时怎样、有什么边界”四句话。

# 四、两个项目的共同主题与差异

## 13. 可以比较的共同思路

| 思路 | Big-Market | Haven |
| --- | --- | --- |
| 不直接执行不可信请求 | 请求先进入应用和领域规则 | 模型提议先过 Schema、Facts、Policy |
| 为副作用建立身份 | 订单号、消息号、业务流水号 | run/call/approval ID 与摘要 |
| 先保存恢复依据 | Outbox、预占记录、待对账任务 | STARTED execution、事件、检查点 |
| 重复安全 | 唯一键、CAS、账户幂等 | 单次审批、前像复核、恢复分类 |
| 不确定时保留状态 | RPC UNKNOWN 待对账 | EFFECT_UNKNOWN 等待 reconcile |

## 14. 不能混为一谈的差异

- Big-Market 面向跨服务业务事实，目标是积分和库存副作用最终正确；Haven 面向本地工具执行，目标是未经验证的副作用不发生、未知副作用不重放。
- Big-Market 的 Outbox 是业务数据与消息任务的事务设计；Haven 的事件日志主要用于审计、UI 投影和恢复。
- Big-Market 的幂等键是业务语义主键；Haven 的摘要绑定当前操作事实，不替代业务幂等。
- Haven 的沙箱不能用于解释 Big-Market 的服务隔离；Big-Market 的最终一致性也不能用于声称 Haven 是分布式工作流系统。

# 五、模拟面试与评分

## 15. 一轮 45 分钟模拟

| 时间 | 内容 |
| ---: | --- |
| 5 分钟 | 自我介绍、工作经历、两个项目定位 |
| 15 分钟 | Big-Market 主链路 + 两个失败场景 |
| 10 分钟 | Java/MySQL/Redis/MQ 基础追问 |
| 8 分钟 | Haven 工具通道或恢复链路 |
| 5 分钟 | 方案取舍和边界 |
| 2 分钟 | 反问与复盘 |

## 16. 每个回答的 10 分评分

| 维度 | 分值 | 判断标准 |
| --- | ---: | --- |
| 直接回答问题 | 2 | 前两句给出结论，不绕背景 |
| 业务流程 | 2 | 有明确入口、顺序和结果 |
| 状态与数据 | 2 | 至少说出一个状态、事务或幂等键 |
| 失败处理 | 2 | 能覆盖超时、崩溃或重复之一 |
| 取舍与边界 | 2 | 不夸大保证，能说复杂度 |

低于 7 分时不要继续背新题，回到[代码阅读记录模板](06-code-reading-template.md)补状态表和失败矩阵。

## 17. 面试前一天只复习这些

1. 两个 30 秒版本；
2. Big-Market 三张图：抽奖、库存、两层 Outbox；
3. Haven 三张图：运行循环、工具通道、恢复分类；
4. 两个项目各三个明确边界；
5. 最近一次模拟中答错的五个问题；
6. 简历专业技能中每一类对应的一个代码事实。

不要在最后一天继续扩展 Chatbot、管理端或新的 Agent 功能。面试稳定性来自把现有主链路讲准确，而不是临时增加覆盖范围。
