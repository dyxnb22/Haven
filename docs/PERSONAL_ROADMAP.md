# Haven 个人开发长期规划

编写：2026-11-06。更新：2026-11-07，用户确认每周可投入 10 小时以上。
状态：持续实施中，已完成项与验证记录见下文。

本文安排接下来约 6–12 个月的工作；只有明确标记完成的命令已经实现。
当前行为以源码、测试和[能力说明](REMAINING_CAPABILITIES.md)为准；
[旧路线图](ROADMAP3.md)保留为历史，已经完成的功能不重新建设。

## 1. 产品目标与工作假设

把 Haven 做成个人愿意日常使用、能够持续维护的本地编码助手：
提出任务，保留项目约定，完成修改和明确验证，必要时暂停、恢复、审阅；
发生失败时知道原因和下一步。

- 一人维护，用户已确认每周可投入 10 小时以上；保守按每周 10 小时排期。
  具体完成日期仍是估算，超出的时间优先用于实际使用、修复和缓冲。
- 优先完善 Python/后端和 CLI 工作流，继续保留已有其他语言支持。
  若前端成为主要用途，调整专项方向。
- 一次推进一个功能，每项包含实现、必要验证和使用说明。
- 时间约 60% 用于功能、25% 用于验证与文档、15% 用于维护。
- S 小项约 4–8 小时，M 中项约 8–24 小时，L 大项约 32–64 小时，均含验证。
  未知集成先做最多 4 小时的调查，再决定范围。
- 每周约安排 6 小时功能开发、2.5 小时验证与文档、1.5 小时维护；
  小项通常用一个迭代，中项拆成 2–3 个迭代。若实际投入下降，顺延而不压缩验收。

### 一年后的可检验目标

| 目标 | 验收方式 |
|---|---|
| 项目约定跨新会话复用 | 可查看、修改、删除；新运行加载并显示来源；其他项目不受影响 |
| 修改有明确验收范围 | 要求 test、lint 两项时，漏项、失败或过期证据均不能满足要求 |
| 长任务可以交接 | 压缩或暂停后，计划、关键决策和未完成检查可追溯；授权仍由程序控制 |
| 常用工程启动顺畅 | 在一个声明支持的工程模板中，初始化、确认配方、修改、验证、审阅可以重复走通 |
| 个人可持续维护 | 安装、升级、恢复可复现；可选集成可关闭和回退，基础工作流仍可用 |

任务成功率、成本下降百分比和与其他产品的差距，需要相同任务、模型、预算的对照。
当前先用具体行为验收，不把这些百分比作为日常功能的发布门槛。

## 3. 全年顺序与优先级

以下按每周 10 小时保守估算，阶段依次推进，窗口可以顺延，不表示并行开发。
目标是在约 3–4 个月内完成主线，约 4–6 个月时推进一个专项；
第 6–12 个月用于稳定使用、发布与维护，不要求填满新功能。

| 阶段 | 建议窗口 | 主要交付 | 粗估投入 | 阶段完成条件 |
|---|---|---|---|---|
| 0：当前版本收口 | 第 1 周 | 能力/指标说明一致、历史管理 | 4–8 小时，超出则拆项 | 现状可核对，清理历史不损伤运行记录 |
| 1：轻量项目记忆 | 第 2–6 周 | 指引查看、空闲刷新、用户主动保存约定 | 16–40 小时 | 约定可见、可删、隔离、跨新会话加载 |
| 2：明确任务验收 | 第 2–3 月 | 验证配置组、一个常用工程工作流、失败反馈 | 24–40 小时 | 要求的检查不会漏跑或被过期结果替代 |
| 3：长任务与模型配置 | 第 3–4 月 | 可审阅交接记录、常用模型配置、局部效率信息 | 24–40 小时，低优先项可后移 | 关键交接信息可恢复，模型与费用展示诚实 |
| 4：选择一个专项 | 第 4–6 月 | LSP、只读并行、前端视觉、编辑器入口之一 | 32–64 小时 | 解决实际困难，可独立关闭和回退 |
| 5：发布与长期维护 | 第 6–12 月 | 安装、升级、恢复走查，控制维护成本 | 24–48 小时，其余作为维护余量 | 新环境可按说明使用，支持范围明确 |

- **P0**：已有安全、数据、恢复、兼容性或事实描述的问题，优先修复。
- **P1**：主线能力，减少日常重复说明、漏验或排查。
- **P2**：依实际需求启动，不阻塞主线。

## 5. 阶段 1：轻量项目记忆

用户故事：重新打开项目时，希望工具保留常用命令和约定，并能查看、纠正这些资料。

### R1.1 查看实际加载的项目指引 — 已完成 / P1 / S

已复用 `AGENTS.md`、`CLAUDE.md` 加载，增加只读查看入口 `/memory`。

验收：

- 展示实际加载的来源、范围、内容和截断情况。
- 未加载时能说明原因；展示已加载快照，与当次上下文对应。
- 内容仍是项目资料，不能改变权限或审批。
- 查看操作不额外读取凭据环境变量或密钥文件，不请求模型，窗口可关闭。

### R1.2 空闲时刷新指引 — 已完成 / P1 / S

已提供 `/memory reload`。外部修改指引后，空闲时显式刷新，
新内容在下一次新运行或后续轮次生效。运行启动、执行、等待回答或等待审阅时阻止刷新。
快照随检查点保存，重启恢复及回答旧任务仍沿用原内容，包括原本没有指引的情况。
没有快照的旧检查点会提示后采用当前指引，保留原有兼容行为。
刷新失败或取消保留原快照；刷新期间拒绝启动任务，TUI 保留误提交的草稿。
只读取实际工作区（隔离时为工作树），不重新加载权限、技能、配方或 MCP。
恢复边界见 [ADR 0044](adr/0044-project-guidance-snapshots.md)。

验收：修改一条约定，刷新后新运行采用它；已有运行及其授权不变。

### R1.3 用户主动保存项目约定 — 已完成 / P1 / M

交付：

- `/remember TEXT` 显式保存到现有用户数据库；规范主工作区身份作为隔离键，
  重启及更换临时工作树后保持归属。
- `/memory` 展示笔记、ID、来源、UTC 创建时间和容量；
  `/memory forget ID` 删除一条，`/memory clear` 清空本项目笔记。
- 限制 20 条、每条 500 字符、正文合计 2000 字符，满额拒绝新增，不逐出旧笔记。
- 与仓库 `AGENTS.md` 分开，作为独立不可信片段进入上下文；
  `debug-context` 也展示已保存的笔记。
- 笔记编辑仅在空闲时进行，不重新读取仓库指引。新运行和后续轮次采用新笔记，
  恢复旧任务仍用保存的快照；删除笔记不改写历史任务。
- SQLite schema 6 增加独立表，已有数据原地迁移。规则见
  [ADR 0045](adr/0045-explicit-project-notes.md)。

验收：保存“这个项目使用 uv 运行命令”后重启仍可见，并进入新上下文；
删除后不再加载；另一项目看不到；恢复旧任务不混入未经说明的新资料。

自动提取、向量检索和跨项目自动共享暂缓。

## 6. 阶段 2：明确本次任务应该验什么

用户故事：修改后，希望知道必须跑哪些检查、哪些通过，
以及失败来自代码、环境还是配置。

### R2.1 用户选定的验证配置组 — 已完成 / P1 / M

已支持“本次必须通过 test 和 lint 两个指定检查”，在运行开始前固定验收范围。
未选组的旧行为保持兼容，命名组不会自动运行命令或改变审批。

交付：

- 用户/项目配置 `[verification_groups]` 把已有 recipe 组成命名组。
  TUI 用 `/verify` 查看、`/verify use NAME` 选择、`/verify clear` 显式清除下一轮要求。
- CLI `--check-group NAME` 选择；后续轮次和执行计划默认继承，
  `--clear-check-group` 可显式清除新轮次要求；`haven continue` 新增可选 `--write`，
  默认仍只读。
- 保存所选要求与完整命令定义摘要，实际检查绑定配方及追加参数，复用
  `repo.check` 和原执行通道。漏项、失败、过期、追加筛选参数及定义不匹配均不能满足要求。
- 模型不能重定义必需配方；策略硬拒绝与执行防线均生效。
  没有文件改动时，执行模式仍需完成所选检查；Plan 保存范围，显式执行后再验证。
- 恢复与回答沿用原范围；缺失/漂移的命令在消耗回答前被拒绝，
  配置中的组被删除或缩小时也不降低已保存任务的要求。
- 面板与门禁共享状态规则，区分通过、失败、未运行、过期和不匹配；
  打开历史任务时以恢复实际使用的检查点账本为准。
- 旧配置、旧检查点默认无组；无组选项的原事件格式与 golden 保持一致。
  使用与恢复规则见[验证组说明](VERIFICATION_GROUPS.md)及
  [ADR 0046](adr/0046-user-selected-verification.md)。

验收：

- 要求两项时，漏一项、任一项失败、最后写入后未重验，都不能满足组要求。
- 模型不能在运行中删除、替换或降低用户要求。
- 无可用检查时明确报告；UI 区分通过、失败、未运行、过期。
- 是否覆盖业务要求仍取决于验收设计，不把无关的通过命令算作语义证明。

### R2.2 打通一个常用工程模板 — 已完成 / P1 / S–M

已用一个 Python 3.12+、src 布局、pytest/Ruff 工程走通初始化预览、
确认配方、固定验证组、小修复、真实检查和工作树审阅应用。
操作步骤和支持范围见 [Python 工程流程](PYTHON_WORKFLOW.md)。

交付：

- 复用 pytest 发现，增加显式 Ruff 配置发现，建议固定的
  `python -m ruff check --no-cache .`；不从注释、字符串或任意项目脚本猜命令。
- `config explain` 展示最终 argv 和实际用户/项目配置来源、超时、
  工作目录规则、环境变量名与固定值、默认/额外可读根目录和网络权限。
  环境规则与执行器使用同一份常量，不打印转发变量的实际值。
- `doctor` 按执行工作区解析可执行文件；同一 Python 环境中的 pytest/Ruff
  依赖缺失会报错并给出下一步，其他解释器明确显示依赖未知。
  只查安装目录中的模块位置，不导入项目同名文件、不启动解释器、不安装依赖。
- 一个离线集成夹具实际运行两种工具，各先失败、修复后再通过，
  核对实际工作树目录、传入沙箱的网络/读取限制和环境过滤；
  查看前主工作区不变，绑定审阅后才应用修改。
  初始化/发现/配置和诊断不调用模型，审阅也不新建模型服务。

实际验证：相关测试 126 项通过，fast 8/8；全量 1434 项通过，
新覆盖率 90%；离线评估 40/40，安全违规和越界改动均为 0。
只增加一个工程流程夹具，不建设新的大规模任务库。
其他模板按实际用途增加，保留已有 Node、Make、Cargo、Go 发现器。

验收：命令来源、工作目录、argv、环境/额外可读路径和网络权限可检查；
依赖缺失有提示；探测不自动安装依赖或信任项目命令。

### R2.3 诊断与验收结果集中展示 — 已完成 / P1 / S

Evidence 页与命令行现已集中展示必需检查状态、最近的进程退出/超时/错误、
诊断文件行号及日志回看命令。操作和上限见[进程输出说明](PROCESS_OUTPUT.md)。

交付：

- 保留 pytest、Mypy、traceback 及编译器解析，补齐当前 Ruff 多行格式及
  Python 诊断中的空格/中文路径。诊断最多 25 条，消息 500 字符，摘要 4000 字符。
- 模型尾部观察保持原上限；独立捕获每流最多 2 MiB 的原文文本，
  超限保留头尾并标明省略字节数。较早错误可从较完整捕获中提取，超时保留已读输出。
- 日志存入现有内容寻址构件；完成事件新增可选展示元数据，
  旧事件缺省为空，非进程事件不附加字段。规则见
  [ADR 0047](adr/0047-retained-process-output.md)。
- `/output` 打开 Evidence 页，`/output CALL_ID` 只读分页查看；
  `haven output RUN_ID [CALL_ID]` 提供概览或日志，支持按行回看和显式完整保留文本导出。
  页面/终端展示有界并转义控制语法，导出拒绝覆盖已有文件。
- 回看地址只从所属运行和调用的事件解析，并校验构件完整性；
  数据库重开后可读，旧调用、缺失或损坏日志明确报错，不重跑命令。
- GC 保留存活事件引用；活动运行暂缓构件清扫，仅清扫开始前已有候选，
  日志带运行/调用身份，保护快照之后新任务的日志。
- 面板只展示最近 10 个进程结果及 50 行证据；验收状态仍取自完整账本。
  普通 exec 的报告和诊断始终不产生检查证据。

实际验证：主组定向 144 项通过，补充的日志/管道/界面与保留策略检查通过；
fast 8/8，全量 1454 项通过，新覆盖率 90%，离线 40/40，安全违规和越界改动均为 0。

验收：较长失败日志能定位主要错误，摘要有上限且可回看原文；
普通 exec 输出不升级成检查证据。

## 7. 阶段 3：长任务交接与模型配置

用户故事：任务变长或被中断后，希望沿着已有决定继续；
同时清楚当前模型、上下文和费用信息是否可信。

### R3.1 可审阅的交接记录 — 已完成 / P1 / M

已支持显式整理、查看和修订五项工作笔记，并分开展示检查点/账本事实。
操作见[长任务交接](HANDOFF.md)，术语见[项目语言](../CONTEXT.md)。

交付：

- `/handoff` 查看事实与笔记；`prepare` 从已有计划标题准备不可信初稿，
  `edit` 编辑已完成、决策及原因、尝试、下一步、待检查事项，`history` 看修订，
  `clear` 显式清除当前采用的笔记。CLI `haven handoff RUN_ID` 提供同样的本地操作，
  支持导出/按已查看日志序号导入 JSON，不创建模型服务。
- 每项最多 600 字符、总计 2000；来源运行、事件、时间及原检查点序号可查看。
  笔记里的完成/权限声明与程序事实分开，不改变权限、验证组或检查证据。
- 修订追加 `handoff.updated` 事件，不重写检查点；只允许暂停/结束的用户任务修改。
  原子比较状态、日志序号和检查点；冲突或输入校验失败保留 TUI 表单。
  SQLite 序号在插入时分配，支持外部修订后的续接，不再复用连接内过期序号。
- 模型运行前冻结编辑窗口，再采用最新显式修订；检查点保存实际使用的快照。
  续接、执行计划与分支继承笔记及来源，新轮次账本仍为空；清除覆盖当前分支继承，
  完全新建任务不自动加载。旧检查点缺省无交接，无需数据库 schema 升级。
- 上下文分别保留不可信笔记和可信账本元数据，先为交接预留空间再丢弃可选技能正文。
  对话压缩不删除独立记录，硬预算仍可对上下文摘录；完整笔记可查看/导出。
- 追问表单增加 Keep paused，保留问题后回到主界面维护交接；`/answer` 可重开，
  Esc 取消任务的原行为保留。恢复与持久化规则见
  [ADR 0048](adr/0048-explicit-task-handoff.md)。

实际验证：相关测试 149 项通过，fast 8/8，全量 1468 项通过，新覆盖率 90%，
离线 40/40，安全违规和越界改动均为 0。一个既有小工程夹具强制压缩、
两次暂停/SQLite 重开后，决策与尝试仍可见，缺失检查仍为未运行，
完成实际 test/lint 后才成功；只读任务不能被笔记授权写入。

验收：用一个现有小夹具强制压缩，再暂停/恢复，关键决定和未完成项可追溯；
程序事实仍来自账本，模型整理的文字是不可信资料；
记录有来源和上限，不影响审批或成功判定。
自动整理需要单独记录信任与持久化决定，并验证是否减少重复工作。

## 13. 暂不进入年度主线

| 事项 | 原因 |
|---|---|
| 自研基础模型、大规模训练 | 投入不适合个人，先用可接入模型改善实际工作流 |
| 云端多租户、远程执行平台 | 运维、隔离、身份和计费形成另一个产品 |
| 多代理同时写入、通用编排 | 合并、授权、预算、恢复的组合成本高 |
| 全语言索引、GraphRAG | 先解决真实定位失败，不以新增数据库为目标 |
| 完整 IDE、移动端、插件市场 | 维护面大，需要时选择一个窄入口 |
| 自动 commit/push/PR | 保持当前不自动修改 Git 历史的边界 |
| 先整理 30–50 个任务评测集 | 不符合当前投入偏好，复用已有检查与自然案例 |

## 14. 每月调整

每月回答四个问题：最常重复处理什么？哪类失败实际出现？
当前最小版本能否完成验收，还是范围正在扩大？下月只做哪一项、哪一项后移？

| 未定事项 | 默认处理 | 决定时机 |
|---|---|---|
| 主力语言/工程 | Python、后端、CLI | 阶段 2 选择实际模板时 |
| 专项方向 | 暂不预选，四选一 | 主线稳定且有具体困难后 |
| 专门付费测量预算 | 默认不额外安排 | 确需验证模型效果时 |

实施后更新本文阶段状态；实际命令和行为仍在 README、能力说明和测试中维护。
一个月只交付一个有用的小功能，也符合这份规划。
